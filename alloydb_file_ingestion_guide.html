Plain-English database guide

Uploading a file to AlloyDB

A file is not usually “converted into AlloyDB” in one step. Your application receives the file, extracts the information you want, and saves that information as database rows. Optionally, it can also create vector embeddings so people can search by meaning.

Is AlloyDB a vector database? Not exactly. AlloyDB for PostgreSQL is a managed, PostgreSQL-compatible relational database. It can store vectors and perform vector similarity searches using its vector (pgvector-based) and alloydb_scann extensions. A useful description is a relational database with vector-search capabilities, rather than a vector-only database.

The file-to-database process

1

Upload

A web app sends the file to your backend service.

2

Extract

The backend reads the text or uses a parser for the file format.

3

Prepare

Clean, split, and optionally summarize the content.

4

Save

Insert document details and text chunks into AlloyDB.

5

Search

Use SQL filters, full-text search, or optional vector search.

What should go into the database?

Document information

Save fields such as the filename, upload time, owner, content type, and processing status. These are ordinary relational columns and work well with SQL filters.

Extracted text

Store the text itself, often as one or more chunks. Chunking makes long documents easier to process, update, and retrieve. Keep a document ID and chunk order so you can relate every piece back to its source.

Original file

For many applications, keep the original file in object storage (for example, Google Cloud Storage) and save its object path in AlloyDB. Store file bytes in the database only when that is an intentional requirement.

Optional embeddings

An embedding is a list of numbers produced by an embedding model from text. Store one for each chunk if you want semantic search. It is not the text itself and does not replace storing the source text.

Two common designs

Design What you store How you search Best starting point when…
Structured text storage Document metadata, extracted text, and optionally summaries. SQL filters, exact matches, or PostgreSQL full-text search. You need a searchable archive or structured records, not “similar meaning” search.
Text plus vector search The same data, plus a vector embedding for each text chunk. Nearest-neighbor similarity search, optionally combined with SQL filters. Users ask natural-language questions or search for concepts with different wording.

You do not need vectors just to upload files. If you only need to preserve text, filter by metadata, or query known fields, use regular relational columns and PostgreSQL search first. Add embeddings when semantic similarity provides a real benefit.

Example database shape

This is an illustrative schema, not a complete production migration. The exact vector dimension depends on the embedding model you choose; confirm it before creating a dimension-specific column or index. 

CREATE TABLE documents (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  filename    text NOT NULL,
  uploaded_at timestamptz NOT NULL DEFAULT now(),
  object_uri  text,
  status      text NOT NULL DEFAULT 'processing'
);

CREATE TABLE document_chunks (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  document_id  bigint NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  chunk_number integer NOT NULL,
  content      text NOT NULL,
  -- Optional: add an embedding column for semantic search.
  UNIQUE (document_id, chunk_number)
);

When adding vector search, enable the AlloyDB vector extension and add a vector column compatible with your chosen embedding model. AlloyDB also offers the alloydb_scann extension for efficient nearest-neighbor indexes. Follow the current AlloyDB documentation for supported versions, index configuration, and query operators.

Where embeddings fit

  1. Split the extracted text into useful chunks, such as paragraphs or transcript sections.
  2. Send each chunk to an embedding model to produce its vector.
  3. Save the chunk text, its document ID, metadata, and vector in AlloyDB.
  4. Create a suitable vector index if needed for your data size and latency requirements.
  5. For a user query, embed the query using the compatible model and search for nearby vectors.
  6. Return the matching text chunks and their source details to the application.

AlloyDB AI can integrate with supported model endpoints and provide SQL functions for generating embeddings. You can also generate embeddings in your application or another service and write the resulting vectors to AlloyDB. Those are different deployment choices; model availability, IAM, extension setup, and permissions need to be configured.

Upload code: browser versus backend

The browser should send the file to your application server. The server validates and parses it, then writes rows to AlloyDB using a database driver and parameterized SQL. Do not put database passwords or cloud credentials in browser JavaScript. 

// Browser-side outline: send a file to your backend, not directly to AlloyDB.
const formData = new FormData();
formData.append("file", selectedFile);

const response = await fetch("/api/documents", {
  method: "POST",
  body: formData
});

if (!response.ok) {
  throw new Error(`Upload failed: ${response.status}`);
}

const result = await response.json();
console.log("Document processing started:", result.documentId);

The endpoint shown here is illustrative. A typical backend flow is: validate upload → store original if required → extract text → write document and chunk rows → optionally generate and store embeddings → report success or failure. For large files, background jobs can keep the upload request responsive and allow retries.

Important design choices

Text extraction

Plain text can be read directly. PDFs, Word documents, scanned images, and audio require appropriate parsers or transcription. Check extraction quality before trusting the database content.

Chunk size and overlap

A whole book may be too large for one model request or one useful search result. Use chunks that retain enough context, and consider a small overlap when splitting continuous text so facts are not cut at boundaries.

Permissions and privacy

Decide who can upload, read, and delete each document. Restrict database access, validate file size and type, and establish retention rules for both original files and extracted text.

Processing errors

Track states such as processing, ready, and failed. Record useful error details, make retries safe, and avoid showing a successful upload when extraction or database insertion failed.

Suggested first version

  1. Accept one supported format, such as plain text, and enforce a reasonable upload limit.
  2. Extract the text on the server and save the filename, text, and upload time in AlloyDB.
  3. Display the saved document and confirm it can be retrieved using SQL.
  4. Add chunking if files are large or you need passage-level results.
  5. Add embeddings and vector indexes only when semantic search is a requirement.
