Plain-English data preparation guide

Preparing your digital knowledge base for an LLM

Your knowledge base may contain links, video transcripts, personal notes, Google Docs, and Sheets. You can use those materials with an LLM in two different ways: let the model look up relevant material when answering (retrieval), or train a model to follow a particular response style or task (fine-tuning). These approaches need different data.

For most personal knowledge bases, start with retrieval (RAG), not model training. Organize and index trustworthy source material, find relevant passages for each question, and give those passages to the LLM at answer time. Fine-tuning is usually better for consistent behavior or output format, not for memorizing a changing library of facts.

First decide what “training” means

Retrieval / RAG: look up your knowledge

Your documents stay in a searchable collection. When you ask something, the system retrieves relevant passages and provides them to the model as context. Update the source collection when your knowledge changes.

Use it for: answering questions about your notes, citing sources, and working with information that changes over time.

Fine-tuning: teach a repeatable behavior

You prepare many examples of inputs and the ideal outputs, then use a provider's fine-tuning process to adjust a supported model. The examples demonstrate a task, tone, or structure; they are not a reliable, searchable copy of all your documents.

Use it for: repeated transformations, a specialized response style, or a consistent output pattern after a simpler prompt has been tested.

Important: fine-tuning availability, accepted file format, minimum examples, pricing, and privacy terms depend on the model provider. Check the current provider requirements before preparing a final training file.

Prepare a knowledge collection for retrieval

  1. Keep the original. Preserve the Google Doc, Sheet, transcript, or source URL. Store a stable link and avoid replacing the source with an AI summary.
  2. Extract readable content. Export or connect to documents with permission. For video, retain transcript timestamps if available. For spreadsheets, keep column headings and enough row context to make each record understandable.
  3. Add metadata. Record title, source type, date, topics, owner or permission scope, and a link back to the original.
  4. Split long material into coherent passages. Use paragraph, section, or topic boundaries. Keep headings with the text they describe; avoid splitting a sentence or table row in half.
  5. Index for search. A retrieval system may use keyword search, vector search, or both. Each indexed passage should retain its source metadata so answers can cite it.
  6. Retrieve, answer, and cite. For each question, pass only relevant passages to the LLM and ask it to distinguish supported facts from uncertainty.

Example of a source passage record

{
  "id": "video-042-chunk-07",
  "source_title": "Interview about sustainable design",
  "source_type": "video_transcript",
  "source_url": "https://example.com/video",
  "location": "00:12:30-00:14:05",
  "topics": ["design", "sustainability"],
  "text": "The speaker explains how repairable parts can extend a product's useful life."
}

The format above is an illustration, not a universal standard. A retrieval system may store passages in a file collection, search index, or database. Keep the text and traceable source information together.

Prepare examples for fine-tuning

Fine-tuning examples should show the model what a good response looks like for a particular task. They should be realistic, consistent, and reviewed by a person who knows the subject.

  1. Define one task. For example, “turn meeting notes into action items in this exact structure.” Avoid mixing unrelated tasks in one dataset.
  2. Create representative inputs. Include different writing styles, source lengths, and common edge cases from your real workflow.
  3. Write ideal outputs. Each output should be correct, useful, and consistent. Include examples where a detail is missing and the right answer is “Not stated.”
  4. Review every pair. Remove invented facts, unsupported claims, inconsistent labels, duplicates, and private information that should not be used.
  5. Split examples before tuning. Keep a separate test set that is not used for training so you can measure whether the tuned model generalizes.
  6. Follow the provider's schema. Many services accept JSON Lines with a conversation per line, but the exact message format and required fields differ.

Illustrative fine-tuning example (JSONL style)

{"messages":[
  {"role":"system","content":"Extract decisions and action items. Do not guess missing owners or dates."},
  {"role":"user","content":"Notes: We agreed to publish the guide next week. Sam will review the draft by Thursday."},
  {"role":"assistant","content":"Decisions:\n- Publish the guide next week.\n\nAction items:\n- Review the draft | Owner: Sam | Due: Thursday"}
]}
{"messages":[
  {"role":"system","content":"Extract decisions and action items. Do not guess missing owners or dates."},
  {"role":"user","content":"Notes: The team wants to revisit the budget. No owner or date was assigned."},
  {"role":"assistant","content":"Decisions:\n- Revisit the budget.\n\nAction items:\n- Revisit the budget | Owner: Not stated | Due: Not stated"}
]}

This sample only demonstrates the idea. It is not guaranteed to match a particular provider's fine-tuning schema. Do not upload it until you have checked the provider documentation and removed sensitive content.

Do not turn every source into a training example

Raw documents are usually retrieval material

A transcript or personal note is a source to search and cite. By itself, it does not tell a training process what response you want the model to produce for a given input.

Training examples need an input and a target

A fine-tuning pair should make the desired behavior explicit: here is an input, and here is the approved answer or transformation. Avoid asking a model to invent “correct” answers from your documents without checking them.

Quality, privacy, and source checks

  • Permission: include only material you have the right to process and use for this purpose. Check licenses, sharing terms, and organizational policies.
  • Personal data: remove or mask confidential details that are not necessary. Understand provider retention and training policies before sending data.
  • Accuracy: check transcripts, names, figures, dates, and spreadsheet context against the originals. Extraction mistakes can become repeated mistakes.
  • Duplicates and conflicts: identify copied notes and outdated versions. Keep dates and version information so newer material does not silently conflict with old.
  • Untrusted instructions: a document may contain text that looks like instructions to the model. Treat source content as data, and test that the system does not follow embedded commands.
  • Traceability: retain source identifiers and locations so a person can verify where a claim came from.

Evaluate before relying on the result

Create a small set of realistic questions and expected answers. Include questions whose answers are not in your material. Check that the system retrieves the right sources, answers accurately, cites evidence, and says when it does not know.

Check What to look for
Source coverage Were the relevant notes, transcript sections, or spreadsheet rows found?
Faithfulness Are claims supported by the source, without invented names, dates, or conclusions?
Citations Do links, page markers, or timestamps lead to the evidence?
Unanswerable questions Does the system clearly say when the knowledge base does not contain an answer?
Consistency Does the output keep the expected structure across different examples?

A practical recommendation

  1. Start with a curated, permission-checked collection of your sources.
  2. Build a small retrieval workflow that returns passages with source links.
  3. Test it with real questions and improve extraction, metadata, chunking, and prompts.
  4. Consider fine-tuning only if you need a consistent behavior that prompting does not reliably achieve.
  5. If fine-tuning, prepare reviewed input/output examples for one task and reserve separate evaluation examples.

Simple rule: use retrieval to give the LLM facts from your changing knowledge base; use fine-tuning to teach a repeatable way of handling inputs. They can be combined, but fine-tuning is not a substitute for a searchable, up-to-date library with source citations.

In brief: organize and clean sources, preserve their provenance, then choose retrieval for knowledge lookup or curated input/output examples for fine-tuning. Evaluate the system and review important outputs before using them.
